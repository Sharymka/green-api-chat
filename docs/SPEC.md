# ТЗ: веб-чат для WhatsApp на GREEN-API

## 1. Цель

Одностраничное React-приложение, через которое пользователь:

1. вводит учётные данные инстанса GREEN-API (`idInstance`, `apiTokenInstance`, `apiUrl`);
2. вводит номер телефона получателя и создаёт чат;
3. отправляет текстовое сообщение в WhatsApp;
4. видит ответ получателя в этом чате.

**Мессенджер — WhatsApp.** Задание допускает WhatsApp вместо MAX; в README коротко объясняем выбор.

Интерфейс максимально простой, внешний вид — по мотивам https://web.max.ru/ (требование задания).

## 2. Границы

**Делаем**

- Экран входа и кнопку «Выйти».
- Список чатов и создание чата по номеру.
- Отправку текста (`SendMessage`).
- Получение текста через HTTP API (`ReceiveNotification` → `DeleteNotification`).

**Не делаем**

| Чего нет | Почему |
|---|---|
| Файлов, фото, голосовых | Задание: только текст |
| Групповых чатов | Минимальный набор функций |
| Сохранения переписки: после перезагрузки страницы чаты пустые | Минимальный набор функций |
| Загрузки старой истории с сервера | Минимальный набор функций |
| Чатов, которые не создал пользователь: сообщения от других номеров не показываются | Сценарий задания: пользователь сам создаёт чат |
| Сообщений, отправленных с самого телефона | Вне сценария |
| Работы нескольких пользователей с одним инстансом | Очередь уведомлений одна на инстанс: два открытых окна «разберут» сообщения между собой |
| Своего сервера: всё работает в браузере | Получение через HTTP API; CORS у GREEN-API открыт (проверено), прокси не нужен |

**Перед запуском пользователю нужно**: создать инстанс WhatsApp в console.green-api.com, авторизовать его по QR; поле `webhookUrl` в настройках инстанса оставить пустым, иначе уведомления не попадут в очередь HTTP API.

## 3. Сценарии

1. **Вход.** Форма → проверка полей → запрос `getStateInstance`. Если `authorized`, открывается чат, иначе понятная ошибка.
2. **Новый чат.** Кнопка «＋» → ввод номера → чат появляется в списке и открывается. Если чат с этим номером уже есть, открывается существующий.
3. **Отправка.** Сообщение сразу появляется в ленте со статусом «отправляется» → «отправлено» или «ошибка» с кнопкой «Повторить».
4. **Получение.** Фоновый цикл забирает уведомления. Входящее текстовое сообщение показывается в чате с тем же номером.
5. **Выход.** Цикл останавливается, данные входа и чаты стираются, открывается экран входа.

### Какие уведомления показываем

- `typeWebhook = incomingMessageReceived`, личный чат (`chatId` вида `79001234567@c.us`), чат с этим `chatId` уже есть в списке.
- Текст берём из `messageData`:
  - `textMessage` → `textMessageData.textMessage`;
  - `extendedTextMessage` (текст со ссылкой) → `extendedTextMessageData.text`;
  - `quotedMessage` (ответ на сообщение) → `extendedTextMessageData.text`.
- Все остальные уведомления удаляем из очереди без показа.

## 4. Дизайн

Отдельный макет не делаем: прототип задан (web.max.ru).

- Цвета, отступы, радиусы — в CSS-переменных.
- Экраны: вход; мессенджер (список чатов слева, переписка справа); заглушка «Выберите чат»; окно нового чата.
- На узком экране одна колонка: список чатов или переписка с кнопкой «Назад».
- Скриншоты — в README.

## 5. Проверка полей

| Поле | Правила |
|---|---|
| `idInstance` | Обязательное, только цифры |
| `apiTokenInstance` | Обязательное, без пробелов; поле-пароль с кнопкой «показать» |
| `apiUrl` | Обязательное, `https://`, домен `*.api.greenapi.com`, `api.green-api.com` или `*.api.green-api.com`. Защита: токен не уйдёт на чужой адрес |
| Телефон | После удаления пробелов, `+`, `-`, `()` — от 11 до 15 цифр; `8XXXXXXXXXX` превращаем в `7XXXXXXXXXX`; для API: `<цифры>@c.us` |
| Сообщение | Не пустое после удаления пробелов по краям; не длиннее 20 000 символов (лимит API) |

Ошибка показывается под полем после попытки отправить форму.

## 6. Загрузка, ошибки, повторы

**Вход**: кнопка показывает загрузку и блокируется. Тексты ошибок:

- `401`/`403` → «Неверный idInstance или apiTokenInstance»;
- статус не `authorized` → «Инстанс не авторизован: отсканируйте QR в личном кабинете»;
- нет сети или ошибка сервера → «Сервис недоступен, попробуйте ещё раз».

**Отправка**: статусы ⏱ отправляется → ✓ отправлено / ⚠ ошибка + кнопка «Повторить». Повтор — по кнопке.

**Получение**:

- `receiveNotification` с `receiveTimeout=20`: запрос ждёт до 20 секунд, следующий отправляется сразу после ответа;
- при ошибке пауза растёт 1 → 2 → 4 … до 30 секунд, сверху плашка «Нет соединения, переподключаемся…»;
- `401` → выход на экран входа с сообщением;
- одно и то же сообщение может прийти дважды (если не прошло удаление), поэтому повторы отбрасываем по `idMessage`;
- цикл запущен ровно один и останавливается при выходе.

## 7. Безопасность

- Данные входа хранятся в `sessionStorage`: живут, пока открыта вкладка, стираются при выходе.
- Данные входа уходят только на проверенный `apiUrl` (см. раздел 5). Токен нигде не логируется.
- Текст сообщений выводится только как текст, без `dangerouslySetInnerHTML` (защита от XSS).
- CSP в `index.html`: запросы разрешены только на домены GREEN-API, скрипты — только свои.
- Внешних скриптов, аналитики и секретов в репозитории нет.

## 8. Доступность (a11y)

- У всех полей есть подписи (`label`); ошибки связаны с полем (`aria-describedby`, `aria-invalid`).
- Всё работает с клавиатуры: Enter отправляет, Shift+Enter переносит строку, Esc закрывает окно нового чата.
- У кнопок-иконок есть `aria-label`; видна обводка фокуса.
- Новые входящие озвучиваются скринридером (`aria-live="polite"`).
- Достаточный контраст текста.

## 11. Тесты

- **Логика**: нормализация телефона; проверка `apiUrl`; разбор уведомлений (три текстовых типа, прочие пропускаются); reducer (отправка, получение, отбрасывание повтора).
- **Компоненты**: вход (успех и ошибка); отправка (успех, ошибка → «Повторить»); входящее появляется в нужном чате. Запросы к API подменяются заглушками.
- **Вручную**: полный сценарий на реальном инстансе с двумя телефонами.
